# Main Viewer

## Overview

## FOV downsampling
The main viewer auto-selects a downsample factor so large FOVs stay responsive while preserving overlays. Allowed factors are the powers of two in `constants.DOWNSAMPLE_FACTORS`; when a FOV loads the viewer samples its dimensions, calls `image_utils.calculate_downsample_factor`, and snaps the result to the nearest permitted value so the longest edge rendered in the notebook remains ≤`constants.DOWNSAMPLE_MAX_DIMENSION`, i.e. 2048 px.

While you pan or zoom, the viewer recomputes the factor from the current viewport and re-renders *before* the canvas rasterises: `ImageDisplay` installs `_render_if_view_changed` as a pre-draw hook (`ueler/viewer/predraw.py`), so the frame ipympl sends already shows the new render. `on_draw` (the `draw_event` handler, which matplotlib fires after rasterising) calls the same function as a fallback and is normally a no-op. The factor comes from `image_utils.screen_downsample_factor`: the largest power of two that still renders at least one image pixel per device pixel of the axes (`ax.bbox`, which under ipympl includes the browser's device pixel ratio), and never less than the `DOWNSAMPLE_MAX_DIMENSION` budget factor. Rendering more pixels than the screen shows only costs time, since Agg resamples them down again. The channel grid applies the same rule per pane. The `Advanced Settings → Downsample` checkbox toggles this behaviour: when enabled, the factor scales with zoom; when disabled, the viewer sticks to native resolution (`factor = 1`).

While the view is dragged with the pan tool the factor is coarsened further, to a preview of at most `viewer.drag_preview_px` rendered pixels across the view (256 by default, `image_utils.drag_preview_factor`). `ImageDisplay` starts the drag on a press with the pan tool inside the axes and ends it on release (or when the pointer leaves the figure); if the last frame was a coarse one it sets `_sharp_render_requested`, marks the axes stale and requests a draw, and the pre-draw hook then renders the same view at the sharp factor. Coarse frames composite fewer pixels and, upscaled on a high-DPI canvas, compress to a PNG several times smaller, which is what matters on a remote connection. `drag_preview_px = 0` keeps every drag frame sharp, and with Downsample off there is no preview.

`Advanced Settings → Frame format` chooses how frames reach the browser (`ueler/viewer/frame_encoding.py`). PNG (the default) is matplotlib's own path: lossless, and either a full frame or a diff with transparent unchanged pixels. With JPEG or WebP, frames that replace most of the canvas (at least 25 % of pixels changed, or a forced full frame) are encoded lossy and sent in `full` image mode; small updates stay PNG diffs and drag previews stay PNG. A lossy full frame is about a third the size of the PNG one, which matters on a slow link to a remote kernel. The setting is `viewer.frame_format`, read at every frame, and is saved with the widget states.

The **initial** factor honours the same checkbox (reply to #116). The size-based `select_downsample_factor` call runs during `__init__` *before* the widgets exist, so after `load_widget_states` restores the saved Downsample preference the viewer reconciles the initial factor: when Downsample is off it starts at native resolution (`factor = 1`), otherwise it uses the size-based factor — matching the `on_draw` path so initiation and zoom agree. The threshold is sourced from `constants.DOWNSAMPLE_MAX_DIMENSION` explicitly at every call site (`main_viewer`, `ImageDisplay.on_draw`, `channel_grid_view`) so the init and zoom thresholds cannot diverge.

Each FOV caches downsampled masks and annotations the first time it loads by slicing the rasters with `array[::factor, ::factor]`. `render_image` reuses those cached arrays and only materialises the visible window, so overlays, plugins, and batch exports share the same subsampled data without additional recomputation.

Channel rasters are cached decoded, not only lazily. In folder mode each channel is a Dask array over one compressed TIFF page, and one page is one Dask task, so slicing any region of it used to read and decompress the whole file again on every render. `ImageMaskViewer.channel_level_cache` (`ueler/rendering/channel_cache.py`) materialises each channel the first time it is rendered and serves every later pan, zoom and FOV revisit from memory; `_compose_fov_image` hands it to the engine as `render_fov_to_array(channel_reader=...)`, so the main view, map tiles and the channel grid all use it. A channel that fits the per-entry cap (an eighth of the budget, 64 MiB by default) is kept at full resolution and every region at every factor is a NumPy view of it, identical to `source[ymin:ymax:f, xmin:xmax:f]`. A larger channel keeps only the downsampled level being viewed (`source[::f, ::f]`), which serves factor-aligned regions; zooming to full resolution on such a channel falls back to the lazy read. The budget is 512 MiB by default, evicted least recently used across FOVs and channels; change it with `viewer.channel_level_cache.set_max_bytes(n)` (`0` disables the cache). Entries remember the array they were decoded from, so a channel replaced in `image_cache` is decoded again, and evicting a FOV from `image_cache` drops its entries. OME-TIFF FOVs (`OMEFovWrapper`) and in-memory arrays are not cached: the former read their own pyramid levels, the latter are already in memory. A read at factor 4 or coarser from a factor-aligned region also keeps a copy of that level (`source[::f, ::f]`, 1/16 of the channel or less) in its own quarter of the budget, so a whole-map overview in map mode, which touches every tile at a coarse factor, can be redrawn from memory after the tiles' full-resolution entries have been evicted.

`get_axis_limits_with_padding` keeps the Matplotlib viewport aligned to factor-sized strides, and the scale bar adjusts via `effective_pixel_size_nm(pixel_size_nm, factor)` so physical measurements remain correct regardless of zoom level. Together this pipeline keeps navigation smooth and measurements trustworthy even on very large scenes.

The shared helper `image_utils.select_downsample_factor` now encapsulates the "snap to `DOWNSAMPLE_FACTORS`" logic, letting plugins such as the ROI browser request the same power-of-two factors with a different max-edge target (256 px for thumbnails).

ROI thumbnails re-compute their factor from each ROI's viewport rather than the parent FOV: the plugin measures the ROI bounds, evaluates `ratio = ceil(longest_edge / 256)`, and emits `factor = 2**ceil(log2(ratio))` (falling back to `1` when the viewport already fits). Rendering helpers also ceil-divide region bounds when deriving downsampled indices so non-divisible widths/heights still cover the entire ROI.
